# 1. 회고에서 메커니즘으로

[설계 노트 목차](README.md) · 다음: [2. 첫 적용과 candidate.4](02-candidates-1-4.md)

Cairn은 빈 설계에서 시작하지 않았습니다. 2026년 9월까지 agent에게 장기간 코드를 맡긴 프로젝트 하나(비공개)가 있었고, 그 프로젝트의 정책 문서·인수 기록·실행 원자료·사후 회고에서 실패와 대응을 골라낸 것이 출발점입니다. 이 문서는 그 추출 과정(2026-09-21)을 요약합니다.

## 1.1 방법

1. 원 프로젝트의 기록에서 "무엇이 잘못될 뻔했고, 무엇으로 막았는가"를 사례 단위로 뽑았습니다(R01~R28).
2. 사례마다 근거의 성격을 구분했습니다. **직접**(원기록을 읽음), **당시 보고**(당시 결과 문서의 진술), **회고**(사후 분석), **정책**(당시 규칙 선언), **설계**(사용자가 이미 승인한 결정). 보고서를 읽은 것을 원자료를 다시 계산한 것처럼 쓰지 않았습니다.
3. 사례마다 일반화할 수 있는 원리와 놓일 자리(core·reusable pattern·adapter·project-specific)를 **후보로만** 적었습니다.
4. 원기록을 한 번 더 대조한 뒤(P0 단계), 겹치는 사례를 7개 메커니즘(UM-01~07)으로 합쳤습니다.

## 1.2 사례에서 뽑은 대표 실패

| 사례 | 일어난 일 | 일반화한 원리 |
|---|---|---|
| R01 | routine 변경마다 승인을 기다렸습니다. 회고는 문서에 남은 사람 개입 묶음(cluster) 59개 중 49개를 routine으로 분류했습니다(실제 메시지 수는 아님) | 이미 위임된 범위는 자율 진행, 고영향 변경만 사람에게 |
| R04 | 하위 교정 네 개를 인수한 뒤에도 전체 프로젝트는 OPEN이었습니다 | 하위 인수는 상위 인수가 아니다 |
| R05 | PASS·commit·push가 인수나 종료와 섞였습니다 | `VERIFIED ≠ ACCEPTED ≠ CLOSED` |
| R06 | 인수한 commit 뒤에 문서 commit이 더해졌습니다 | 검증한 대상과 전달한 대상의 identity를 따로 대조 |
| R08 | 기계 검사는 PASS였는데 사용자에게 필요한 질문이 실제로 빠져 있었습니다. 독립 검토가 FAIL을 냈고, 첫 수정 뒤에도 재발했습니다 | 실제 결과를 기준으로 한 독립 검토, 원 FAIL 보존 |
| R09 | 생성자의 자기평가가 검토자를 오염시킬 수 있었습니다 | 검토자에게 원자료는 주고 자기평가·설득은 주지 않는다 |
| R10 | 새 맥락으로 띄운 하위 agent가 범위 밖 파일을 읽었습니다 | 논리적 독립과 실제 접근 통제는 다르다. 격리를 과장하지 않는다 |
| R12 | 종료 event가 유실됐고, 시작·종료가 불명확한 실행을 다시 돌리면 중복될 수 있었습니다 | 불명확한 외부 효과는 자동 재실행하지 않는다 |
| R16 | 많은 회귀 PASS 뒤 전수 감사에서 독립 원인 결함 3건이 나왔습니다 | 검사 수·매핑 완전성은 정확성이 아니다 |
| R19 | "상시 로드 아님"이라고 적힌 문서 링크가 개발 역사를 실행 맥락으로 끌어왔습니다 | 현재 계약과 역사를 분리, 필요한 만큼만 단계적으로 회수 |
| R22 | 회고 분석값으로 병렬화 지원 코드 +3,188줄 대 제품 코드 +403줄, 상태 불일치 5건 | 실제 실패를 막는 최소 장치만 남긴다 |
| R28 | 제품 고유의 Skill 7개·도메인 기록·수량 상수 | Universal 규칙에서 제외 |

R22의 수치는 당시 회고가 낸 값이며, 이번에 다시 계산하지 않았습니다. 관리 구조 전체가 낭비였다는 근거로도 쓰지 않았습니다.

## 1.3 일곱 메커니즘

| ID | 이름 | 막는 실패 | 강도 |
|---|---|---|---|
| UM-01 | 한정된 권한과 명시적 상향 판단 | 작업 허가가 기준 완화·통합 권한으로 번지거나, 위임된 일마다 다시 승인을 요구하는 것 | Invariant |
| UM-02 | 산출물에 결합된 주장과 명시적 적용성 | 검증한 것과 인수·전달한 것이 달라지는 것, 새 성공이 과거 실패를 덮는 것 | Invariant |
| UM-03 | 범위별 검증·인수·종료 | PASS를 인수로, 하위 인수를 상위 인수로, 인수를 종료로 오인하는 것 | Invariant |
| UM-04 | 필수 판단의 독립성 | 생성자의 자기평가로 독립 판단을 가장하는 것, 수정자가 자기 수정을 인수하는 것 | Invariant(독립 판단이 요구된 경우) |
| UM-05 | 위험·범위에 따른 검증 | 검사 수를 정확성으로 착각하거나, 사소한 변경에도 전수 감사를 반복하는 것 | Default policy |
| UM-06 | 실행 대조를 통한 한정 복구 | 중단 뒤 이미 시작한 효과를 중복 실행하거나, 통과할 때까지 재시도하는 것 | Reusable pattern |
| UM-07 | 최소 정본 맥락과 파생 탐색 | 오래된 인계를 현재 권위로 읽거나, 한 절을 찾으려고 전체 역사를 읽는 것 | Default policy |

강도는 성숙도 단계가 아닙니다. **Invariant**는 어기면 권한·판정의 의미가 성립하지 않는 규칙, **Default policy**는 프로젝트가 한정된 다른 정책을 선언할 수 있는 규칙, **Reusable pattern**은 필요할 때만 부르는 절차입니다. 실제 강제·관측 수단은 runtime adapter의 몫으로 남겼습니다.

이 일곱 개가 지금 Cairn 계약의 뼈대입니다. 권한 교집합(`Role ∩ Node ∩ Scope`), 네 상태, 비producer 인수, Human Gate, evidence의 candidate 결합, progressive retrieval이 각각 여기서 나왔습니다.

## 1.4 가져오지 않은 것

| 원 프로젝트에 있던 것 | 처리 | 이유 |
|---|---|---|
| 모든 주요 단계의 사람 인수, 고정 반복 수(3회 등), 매번 최종 감사 | 제외 | 당시 작업량과 사용자 기준이다. 필요하면 프로젝트 설정으로 둔다 |
| 대형 snapshot·중복 원장·병렬 실행기 | 제외 | 직접 실패를 막는 의미는 UM-01~07로 남길 수 있다. 관리 규모를 정당화할 보편 효과 자료가 없다 |
| 역할 9개를 모두 별도 세션으로 띄우는 규칙 | 제외 | 독립 판단에는 맥락 분리가 필요하지만, 새 세션은 여러 수단 중 하나다 |
| Git SHA 전용 identity | adapter로 | identity라는 의미는 Core, 구체 수단은 runtime·저장소에 따라 다르다 |
| 그래프 DB·벡터 검색·전수 요약 | 제외 | Artifact Graph는 정본의 명시 참조에서 결정적으로 뽑는 탐색 단서로만 둔다 |

## 1.5 이 단계에서 주장하지 않은 것

- Review Brief의 효과, 역할별 독립 세션의 필요성, 인계만으로 복구되는 비율, Artifact Graph의 실제 token 절감은 측정하지 않았습니다.
- 원 프로젝트의 테스트 모음이나 원실행을 다시 돌리지 않았습니다. 원기록을 읽은 범위는 사례마다 따로 적었습니다.
- 이 일곱 메커니즘으로 소형 프로젝트(Booklog)의 일반 변경이 가벼울 것이라는 판단은 **설계상 부담 점검**이었습니다. 실제 적용 결과는 [다음 문서](02-candidates-1-4.md)에 있습니다.
